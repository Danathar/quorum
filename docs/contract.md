# Quorum contracts

Three boundaries, versioned together. Every component in hive, quorum and spektacular builds against this file. Version: `quorum.contract/v1`.

## Process model

Quorum runs **inside the hive container** as a child process that hive starts and supervises, the same way hive runs the `spektacular` binary. It listens on loopback only. No extra container, no pod spec change, no hub change.

- Binary: `quorum serve` (Node 22, published as `@hivecommons/quorum` and baked into the hive image).
- Listen: `QUORUM_LISTEN` (default `127.0.0.1:8765`). MCP endpoint `POST /mcp` (streamable HTTP). Health `GET /healthz`.
- Auth: bearer token from `QUORUM_TOKEN_FILE`, generated by hive per boot and passed to the child.
- Vexa: `QUORUM_VEXA_URL` (gateway base URL), `QUORUM_VEXA_API_KEY_FILE` (tenant key; hive writes it from its keystore).
- Discord: `QUORUM_DISCORD_TOKEN_FILE` (per-hive bot token, optional; Discord tools return `platform_unavailable` without it).
- Whisper for Discord audio: `QUORUM_TRANSCRIBE_URL` (the shared CPU transcription service).
- Every numeric limit in this file is an env var with the default shown.

## 1. Quorum MCP tools (hive is the client)

All tools return `{ok: true, ...}` or `{ok: false, error: {code, message}}`. Error codes: `invalid_argument`, `not_found`, `platform_unavailable`, `blocked` (meeting refuses guest bots), `lobby_timeout`, `not_live`, `rate_limited`, `upstream_error`.

| Tool | Arguments | Result |
|---|---|---|
| `meeting.join` | `{url, display_name, platform?}` platform inferred from URL: `google_meet`, `teams`, `zoom`; Discord uses `{platform:"discord", guild_id, channel_id}` | `{meeting_id, platform, state}` |
| `meeting.leave` | `{meeting_id}` | `{state}` |
| `meeting.status` | `{meeting_id}` | `{state, participants:[{id,name}]}` |
| `transcript.read` | `{meeting_id, after_seq?}` | `{segments:[Segment], next_seq}` |
| `chat.post` | `{meeting_id, text}` text max `QUORUM_CHAT_MAX_CHARS`=2000 | `{posted_at}` |
| `say` | `{meeting_id, text}` | `{queued:true}`; `platform_unavailable` when the bot was started without voice |
| `meeting.delete` | `{meeting_id}` | `{deleted:true}` erases transcript upstream |

Live streaming: hive opens `GET /events?meeting_id=...` (Server-Sent Events, same bearer) and receives one JSON object per event:

- `{"type":"segment", "meeting_id", "seq", "speaker":{id,name}, "text", "start", "end", "final"}`
- `{"type":"chat", "meeting_id", "seq", "author":{id,name}, "text", "at"}`
- `{"type":"state", "meeting_id", "state", "reason?"}` where `state` is one of `requested, joining, lobby, live, ended, failed, blocked`.

`Segment` = the `segment` event without `type`.

## 2. Spektacular live mode (hive runs it as a child)

`spektacular meeting --from stdin --format jsonl --title <t> --context <dir>`

One JSON object per line in both directions. Unknown fields are ignored; unknown `type` values are logged and skipped.

stdin (hive to Spek):

- `{"type":"segment", ...}` exactly the Quorum segment event (only `final:true` segments are sent)
- `{"type":"chat", ...}` meeting chat lines from people
- `{"type":"answer", "qid", "text", "by"}` a reply hive matched to an earlier `ask`
- `{"type":"research_update", "rid", "status":"queued|running|done|failed", "summary?", "url?"}`
- `{"type":"end"}` meeting over; Spek flushes notes and exits 0

stdout (Spek to hive, called intents):

- `{"type":"chat.post", "text"}`
- `{"type":"ask", "qid", "text"}` a clarifying question; hive posts it and routes the next reply as `answer`
- `{"type":"notes.append", "section", "text"}` sections: `decisions`, `actions`, `questions`, `summary`, `notes`
- `{"type":"research", "rid", "query", "reason"}`
- `{"type":"say", "text"}` only when the meeting addressed hive by name; hive decides whether voice is allowed
- `{"type":"heartbeat"}` at least every `SPEK_MEETING_HEARTBEAT_S`=15 seconds

Spek never calls Quorum directly. Hive is the policy point: budgets, rate limits, voice rules and consent are enforced in hive before anything reaches the meeting.

Behaviour targets: act on final segments only; ask at pauses longer than `SPEK_MEETING_PAUSE_MS`=1500; at most `SPEK_MEETING_MAX_ASKS_PER_10M`=3 questions per 10 minutes; never repeat a question; "hive, research X" and close variants are explicit research; implicit mentions ("we should look into X") become an offer via `chat.post` and only become `research` after someone agrees.

## 3. Hive meeting API and research return

- `POST /api/meetings {url | platform+guild_id+channel_id, voice?:bool}` owner-only, returns the meeting record.
- `GET /api/meetings`, `GET /api/meetings/{id}`, `POST /api/meetings/{id}/leave`, `POST /api/meetings/{id}/voice {enabled}`, `POST /api/meetings/{id}/research/{rid}/approve`.
- `GET /api/meetings/{id}/ws` live panel: transcript, intents, research status.
- Research: each `research` intent becomes a kick to the research agent pool with a kick ID; `[FINDING]` and `[COMPLETE]` signals for that kick come back as `research_update` to Spek and a `chat.post` summary (max one per research item) plus a knowledge fact under the meeting's notes.
- On join hive posts the consent notice (`meetings.consent_text`) before anything else. `hive leave` typed in chat or said to hive makes it leave.
